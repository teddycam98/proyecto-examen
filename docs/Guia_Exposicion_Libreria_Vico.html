SECCIÓN 2: ¿DE QUÉ SIRVE Y CÓMO AYUDA A MEJORAR EL SISTEMA?

Si el docente les pregunta: "¿Cuál es el beneficio real de este proyecto frente a seguir usando Excel o un cuaderno?", esta es la fundamentación que deben exponer:

Problema en la Librería Consecuencia Negativa Real Cómo lo Resuelve Nuestro Sistema
Venta de artículos agotados Pérdida de clientes, quejas y mala reputación en mostrador. Validación en tiempo real: El POS consulta las existencias antes de confirmar y descuenta el stock en la misma transacción. Si el stock llega a 0, se bloquea la adición.
Lentitud al cobrar Filas de espera de 10 a 15 minutos en temporada escolar de alta demanda. Punto de Venta reactivo: Selección con botones táctiles `+` y `−`, cálculo automático de precios y confirmación en menos de 30 segundos.

SECCIÓN 3: LA ARQUITECTURA MVC EXPLICADA EN SENCILLO

El patrón Modelo - Vista - Controlador (MVC) es un patrón de diseño arquitectónico que divide el código en tres responsabilidades fundamentales para que el proyecto sea mantenible, ordenado y escalable.

1. LA VISTA (Frontend / Interfaz de Usuario)

¿Qué es? Es lo que el usuario ve en la pantalla de su computadora o celular (páginas HTML, estilos CSS y comportamiento visual con JavaScript).
¿Dónde está en el código? En las carpetas backend/src/main/resources/vista/ y static/.
¿Qué hace? Muestra los botones, el catálogo con fotos, el carrito de compras y las tablas de datos usando Thymeleaf y Bootstrap.
Regla de oro: La vista NUNCA debe contener lógica de negocio pesada ni conectarse a la base de datos; solo muestra información y envía peticiones al Controlador.

2. EL CONTROLADOR (Spring MVC / Controller)

¿Qué es? Es el "recepcionista" o "policía de tráfico" del sistema. Es la puerta de entrada a la que llegan las peticiones HTTP que envía el navegador.
¿Dónde está en el código? En el paquete com.proyectoexamen.backend.controller (ej. SaleController.java, ProductController.java).
¿Qué hace? Recibe los datos que envió el usuario, verifica que los formularios cumplan las validaciones básicas (ej. que el DNI tenga 8 dígitos con @Valid), llama al Servicio correspondiente y decide qué vista devolver al usuario.
Regla de oro: El controlador NUNCA interactúa con la base de datos directamente; su único trabajo es recibir la solicitud, llamar al servicio y encaminar la respuesta.

3. EL SERVICIO (Lógica de Negocio / Service & ServiceImpl)

¿Qué es? Es el "cerebro" y el corazón comercial del sistema. Aquí residen todas las reglas del negocio de la librería.
¿Dónde está en el código? En los paquetes service y service.impl (ej. SaleServiceImpl.java, ProductServiceImpl.java).
¿Qué hace? Aplica las condiciones del mundo real: ¿Hay suficiente stock para vender? ¿El precio de venta es mayor que el costo? ¿El cliente ingresó un comprobante válido? Si todo es correcto, calcula subtotales, descuenta existencias y genera el Kardex.
Regla de oro: Aquí se coloca la anotación @Transactional. Si una venta tiene 5 productos y el quinto falla, la transacción revierte todo (*Rollback*) para no dejar el inventario descuadrado.

4. EL REPOSITORIO (Capa de Acceso a Datos / DAO)

¿Qué es? Es el "puente" de comunicación entre el código Java y la base de datos MySQL.
¿Dónde está en el código? En el paquete com.proyectoexamen.backend.repository (ej. ProductRepository.java, SaleRepository.java).
¿Qué hace? Hereda de JpaRepository de Spring Data JPA. Permite buscar, guardar, actualizar o eliminar registros en la base de datos utilizando métodos Java limpios (como save() o findById()) sin necesidad de escribir extensas consultas SQL manuales repetitivas.

5. EL MODELO / ENTIDAD (Entity)

¿Qué es? Son las clases Java que representan directamente a las tablas físicas de la base de datos.
¿Dónde está en el código? En el paquete com.proyectoexamen.backend.entity (ej. Product.java, Sale.java, Category.java).
¿Qué hace? Con la anotación @Entity y @Table, Hibernate sabe que cada propiedad de la clase (como private String name;) se mapea con una columna de MySQL. Además, define relaciones como @ManyToOne o @OneToMany.

6. LA BASE DE DATOS (MySQL en TiDB Cloud Serverless)

¿Qué es? El motor relacional físico en la nube donde los datos se almacenan de forma permanente y segura bajo el motor transaccional InnoDB.
¿Cómo se gestiona? Mediante Flyway, que corre scripts SQL evolutivos (V1 a V5) creando tablas y productos automáticamente al arrancar la aplicación.

SECCIÓN 4: LA ANATOMÍA DE UN CLIC

¿Qué sucede exactamente en el código cuando el cliente hace clic en "Confirmar Venta"?

Esta es una de las preguntas técnicas más valoradas por los docentes universitarios y técnicos: "Explícame el recorrido completo de los datos desde que el usuario presiona un botón hasta que se guarda en la base de datos". Aquí tienes el paso a paso exacto:

PASO 1: En el Navegador del Usuario (JavaScript y DOM)

El usuario está en el Punto de Venta (/ventas/nueva), agrega al carrito 2 unidades del "Cuaderno Stanford A4" y hace clic en el botón azul "Confirmar venta". En ese instante, el script app.js intercepta el evento. En lugar de enviar datos desordenados, genera dinámicamente campos ocultos dentro del formulario HTML:

<input type="hidden" name="items[0].productId" value="7">
<input type="hidden" name="items[0].quantity" value="2">

El formulario empaqueta el nombre del cliente, el DNI y la lista de artículos, y despacha una petición HTTP con método POST hacia la ruta /ventas.

PASO 2: La Petición Viaja por la Red hacia el Servidor Cloud

La petición viaja por internet cifrada bajo el protocolo seguro HTTPS (TLS) hacia nuestro contenedor Docker alojado en Render.com. El servidor web embebido (Apache Tomcat en Spring Boot) recibe la solicitud en el puerto dinámico y la entrega al despachador central de Spring: el DispatcherServlet.

PASO 3: Llegada a la Capa Controlador (SaleController.java)

El DispatcherServlet detecta que la URL es POST /ventas y redirige la petición al método correspondiente en SaleController.java:

@PostMapping
public String create(@Valid @ModelAttribute SaleForm saleForm, BindingResult result, ... )

Aquí ocurren dos cosas automáticas muy importantes: 1. Data Binding: Spring convierte los campos del formulario en un objeto Java llamado SaleForm (un DTO). 2. Validación: Con la anotación @Valid, comprueba que el DNI cumpla la expresión regular (8 u 11 dígitos numéricos). Si hay errores de formato, rechaza la operación sin tocar la base de datos. Si no hay errores, el controlador invoca a la capa de servicio: saleService.create(saleForm);.

PASO 4: Ejecución en la Capa de Lógica de Negocio (SaleServiceImpl.java)

Aquí entra a tallar el método create(SaleForm form) anotado con @Transactional. Se ejecutan las siguientes reglas de negocio en orden estricto:

  • Normalización: Con el método normalize() consolida productos duplicados y verifica que ninguna cantidad sea menor o igual a cero.
  • Generación de Comprobante: Genera un código correlativo único mediante generateNumber("V") (ej. V-20261022150856-760B).
  • Consulta y Bloqueo de Producto: Llama a productRepository.findByIdForUpdate(productId) para cargar los datos del producto desde MySQL.
  • Validación de Existencias: Comprueba if (product.getStock() < quantity). Si no hay suficiente stock, lanza una BusinessException y la venta se detiene protegiendo el negocio.
  • Descuento del Stock: Calcula el nuevo stock (int updated = previous - quantity;) y actualiza la entidad en memoria: product.setStock(updated);.
  • Cálculo de Totales: Multiplica la cantidad por el precio de venta unitario y lo acumula en el total de la venta en Soles (S/).
  • Registro en el Kardex: Invoca a stockService.record(...) para dejar constancia histórica de que salieron 2 unidades por motivo de "VENTA".
PASO 5: Capa de Persistencia y Generación de SQL (Hibernate / JPA)

Al finalizar el método, se ejecuta saleRepository.save(sale);. Aquí entra en acción Hibernate, el motor ORM de Spring Data JPA. Hibernate traduce los objetos Java a instrucciones SQL nativas para MySQL:

INSERT INTO sales (sale_number, sale_date, customer_name, total, status, ...) VALUES (...);
INSERT INTO sale_items (sale_id, product_id, quantity, unit_price, subtotal) VALUES (...);
UPDATE products SET stock = 13, version = version + 1 WHERE id = 7 AND version = 0;
INSERT INTO stock_movements (product_id, movement_type, quantity, previous_stock, new_stock, ...) VALUES (...);

¡Fíjate en el UPDATE de productos! Al actualizar, incrementa el campo version = version + 1. Ese es el bloqueo optimista que garantiza que nadie haya modificado el producto mientras nosotros realizábamos la venta.

PASO 6: Confirmación en la Base de Datos Cloud (TiDB Cloud)

Las sentencias SQL se transmiten por la red mediante el driver mysql-connector-j hacia nuestro cluster de TiDB Cloud en AWS. El motor InnoDB ejecuta todas las inserciones y modificaciones de forma atómica y realiza el COMMIT. Los datos quedan guardados de forma indestructible en la nube.

PASO 7: Respuesta al Navegador (Patrón Post-Redirect-Get)

Una vez guardada la venta con ID = 4, el controlador no devuelve un HTML directamente, sino una redirección HTTP 302:

return "redirect:/ventas/" + sale.getId();

Esto implementa el estándar de la industria llamado Post-Redirect-Get (PRG). ¿Para qué sirve? Evita que si el cliente presiona F5 o recarga la página, la venta se vuelva a registrar por duplicado. El navegador solicita automáticamente GET /ventas/4, el servidor procesa la plantilla detail.html con Thymeleaf y el cajero ve en su pantalla el comprobante verde con los productos, el total cobrado y el stock actualizado. ¡Todo este ciclo tomó menos de 400 milisegundos!

SECCIÓN 5: BANCO DE PREGUNTAS DIFÍCILES DEL DOCENTE

Los profesores suelen hacer preguntas técnicas para comprobar si los estudiantes realmente entienden el código o si solo copiaron una plantilla. Aquí tienen las respuestas exactas:

Pregunta 1: "¿Por qué colocaron @Transactional en los servicios y no en los controladores?"

Respuesta perfecta: "Porque los controladores pertenecen a la capa de presentación web, mientras que las transacciones pertenecen a la lógica de negocio. Una operación comercial puede involucrar guardar la venta, descontar stock de varios productos y crear registros en el Kardex. Si colocáramos la transacción en el controlador, estaríamos acoplando la tecnología HTTP con la lógica de base de datos. Al tener @Transactional en el Service, aseguramos que si cualquier producto falla, toda la transacción se revierte con un Rollback atómico sin importar desde dónde se invoque el servicio."

Pregunta 2: "¿Qué pasa si dos personas intentan comprar el último cuaderno al mismo tiempo?"

Respuesta perfecta: "Para solucionar eso implementamos Control de Concurrencia Optimista mediante la anotación @Version en la entidad Product. Cada vez que se descuenta el stock, Hibernate ejecuta un UPDATE verificando que la versión coincida con la que se leyó inicialmente. El primer cajero que confirme actualizará el registro e incrementará la versión a 1; cuando el segundo cajero intente confirmar, Hibernate detectará que la versión ya no coincide, lanzará una excepción de concurrencia y no permitirá la venta de stock inexistente, protegiendo al negocio de inventarios negativos."

Pregunta 3: "¿Por qué el controlador nunca debe llamar a un repositorio directamente?"

Respuesta perfecta: "Porque violaría el principio de responsabilidad única de la arquitectura MVC y de los principios SOLID. Si un controlador consulta directamente el repositorio, se saltaría las validaciones de negocio, los límites transaccionales y las reglas de seguridad. Toda interacción con los datos debe pasar por la capa de servicio para garantizar la coherencia de la información."

Pregunta 4: "¿Cómo funciona JasperReports y por qué no usaron una librería JavaScript de PDF como jsPDF?"

Respuesta perfecta: "Librerías de frontend como jsPDF generan el documento en el navegador del cliente basándose en capturas HTML, lo cual puede ser manipulado alterando el DOM con las herramientas de desarrollador. En cambio, JasperReports es un motor empresarial compilado del lado del servidor en Java: consulta directamente los datos auditados desde el servicio, compila la plantilla con la API JasperDesign, inyecta fuentes tipográficas DejaVu Sans y genera un flujo de bytes PDF inmutable y fidedigno, ideal para auditorías comerciales y contables."

Pregunta 5: "¿Por qué eligieron TiDB Cloud y no una base de datos local o PostgreSQL?"

Respuesta perfecta: "Porque TiDB Cloud es una base de datos distribuida de última generación nativa en la nube, con cumplimiento estricto de estándares ACID y 100% compatible con el protocolo y dialecto de MySQL 8. Al ser Serverless, nos permite tener alta disponibilidad 24/7 en internet sin costo mensual de infraestructura y sin depender de que nuestra computadora personal esté encendida para que el sistema funcione."

Pregunta 6: "¿Dónde está la pantalla de Login con usuarios y contraseñas?"

Respuesta perfecta: "Profesor, en esta entrega académica priorizamos el núcleo transaccional del negocio: control estricto de existencias, punto de venta reactivo, trazabilidad tipo Kardex, generación de reportes con JasperReports y despliegue continuo en la nube con Docker. La separación funcional entre los perfiles de Administrador y Vendedor ya está establecida a nivel de arquitectura, y la integración de Spring Security con tokens JWT y encriptación BCrypt es la primera línea de escalabilidad para la siguiente fase."
